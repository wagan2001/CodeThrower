# Local LLM Coding Dojo Desktop App Strategy

## 1. Product Vision

Build a self-contained desktop application that acts like a local coding dojo coach.

The app should let a user choose a programming language, describe what they want to practice in that language, select a difficulty level, and then receive a custom practice problem generated by a local LLM. The same local model should provide progressive hints, evaluate the user's answer, and generate follow-up practice recommendations.

The app should feel less like a chatbot and more like a structured skill-building rep machine.

Core loop:

```text
Pick skill → Generate rep → Attempt → Hint if stuck → Submit → Score → Diagnose weakness → Generate next rep
```

The north-star goal is a local AI practice partner that can create infinite, targeted programming reps without requiring cloud inference.

---

## 2. Target Hardware Constraint

The app should be able to run on a machine with an 8 GB GPU.

This means the baseline model strategy should avoid large models. The app should target small quantized coding models and use structure, prompts, validation, and application-side logic to compensate for model limitations.

Recommended model tiers:

```text
Default balanced model:
Qwen2.5-Coder 7B Instruct GGUF, Q4_K_M or similar quantization

Fallback lightweight model:
Qwen2.5-Coder 3B Instruct GGUF

Tiny compatibility mode:
1.5B–3B coder model

Optional external runtime during development:
Ollama with qwen2.5-coder:7b-instruct
```

Avoid requiring 14B, 30B, or larger models for the baseline experience.

---

## 3. Recommended Architecture

For a true self-contained desktop application, the preferred architecture is:

```text
Tauri desktop shell
  ↓
React + TypeScript frontend
  ↓
Rust backend commands
  ↓
llama.cpp server sidecar
  ↓
Local GGUF coding model
  ↓
SQLite session database
  ↓
Optional code execution sandbox
```

Recommended production-ish stack:

```text
Desktop framework: Tauri
Frontend: React + TypeScript
Editor: Monaco Editor
Backend/controller: Rust via Tauri commands
Local model runtime: llama.cpp server sidecar
Model format: GGUF
Database: SQLite
Packaging: Tauri bundler
Optional sandboxing: Docker or restricted local subprocess execution
```

Recommended development stack:

```text
Tauri or Electron frontend
React + TypeScript UI
Ollama as temporary model runtime
SQLite or local JSON for session history
No sandboxed execution at first
```

The fastest development path is to prototype against Ollama first, then replace Ollama with a bundled llama.cpp sidecar once the product loop works.

---

## 4. Why Tauri Instead of Electron

Tauri is recommended for this app because the app is intended to be a lightweight local utility that may also launch and manage a heavy model process.

Advantages:

- Smaller application footprint than Electron.
- Rust backend is well-suited for process management.
- Good fit for launching a bundled inference binary as a sidecar.
- Better long-term fit for a local-first desktop tool.

Electron is still reasonable for a fast prototype, especially if the builder wants the easiest JavaScript-only path. But for the final self-contained version, Tauri is the stronger target.

## 5. Local Model Runtime Strategy

There are two possible runtime modes.

### Development Mode

Use Ollama as the model provider.

Benefits:

- Very easy to set up.
- Simple local HTTP API.
- Easy model switching.
- Good for validating the product loop before dealing with packaging.

Example development model:

```text
qwen2.5-coder:7b-instruct
```

### Self-Contained Mode

Use llama.cpp server as a bundled sidecar.

Benefits:

- No external Ollama dependency.
- App can own the lifecycle of the model server.
- Works with GGUF models.
- Better fit for an installable desktop application.
- Can expose OpenAI-compatible local endpoints.
- Can support schema-constrained JSON output depending on runtime configuration.

Startup flow:

```text
1. App launches.
2. Backend checks whether a model exists locally.
3. Backend starts llama.cpp server as a sidecar process.
4. Frontend waits for model health check.
5. User starts a practice session.
6. Problem generation, hints, and scoring call the local model server.
7. On app close, backend shuts down the model process.
```

## 7. Main User Flow

The app should guide the user through a simple dojo setup.

### Step 1: Language

Ask:

```text
What language do you want to learn?
```

Example answers:

```text
Python
SQL
JavaScript
TypeScript
Rust
C++
Java
Go
```

### Step 2: Practice Topic

Ask:

```text
What do you specifically want to practice?
```

This should be open-ended.

Example answers:

```text
pandas groupby
recursion
binary search
SQL window functions
async JavaScript
Rust ownership
object-oriented design
debugging edge cases
writing cleaner functions
```

### Step 3: Difficulty

Ask the user to choose:

```text
Beginner
Intermediate
Advanced
Interview
Expert
Adaptive
```

### Step 4: Mode

Optional but valuable:

```text
Guided
Test me
Debugging
Refactor
Explain-first
```

### Step 5: Generate Problem

The model generates:

- Title
- Scenario
- Problem statement
- Examples
- Constraints
- Starter code
- Expected concepts
- Public tests
- Hidden tests
- Canonical solution
- Rubric

The user should not see the canonical solution or hidden tests unless they explicitly give up.

### Step 6: User Solves

The user writes code in a Monaco editor.

The app provides buttons:

```text
Get hint
Submit answer
Reset
Show problem details
Generate similar problem
Make it harder
Make it easier
```

### Step 7: Hint Ladder

Hints should be progressive:

```text
Hint 1: Small conceptual nudge
Hint 2: Stronger direction
Hint 3: Algorithm-level explanation without full code
```

### Step 8: Scoring

The app scores the submission using:

```text
Correctness
Edge cases
Code quality
Complexity
Concept mastery
```

Initial MVP can use LLM-only grading.

Later versions should combine:

```text
Automated tests + LLM critique
```

### Step 9: Next Rep

The app recommends the next practice problem based on the user's mistake pattern.

Example:

```text
You handled the main path correctly but missed empty input and duplicate keys.
Next rep: a similar dictionary problem with duplicate handling and missing values.
```

## 10. Prompt Strategy

Small local models behave better when prompts are strict, short, and schema-driven.

Do not rely on one large vague prompt.

Use separate prompts for:

```text
Problem generation
Hint generation
Scoring
JSON repair
Follow-up recommendation
```

---

## 11. Problem Generation Prompt

```text
You are a coding dojo problem generator.

Create one practice problem.

Language: {language}
Topic: {topic}
Difficulty: {difficulty}
Mode: {mode}

Return valid JSON only.

Schema:
{
  "title": string,
  "problemStatement": string,
  "examples": [
    {
      "input": string,
      "output": string,
      "explanation": string
    }
  ],
  "constraints": string[],
  "starterCode": string,
  "expectedConcepts": string[],
  "publicTests": string[],
  "hiddenTests": string[],
  "canonicalSolution": string,
  "rubric": {
    "correctness": 50,
    "edgeCases": 20,
    "codeQuality": 15,
    "complexity": 15
  }
}

Rules:
- The problem must be solvable in 15 to 45 minutes.
- The problem must match the requested language and topic.
- Avoid trivia.
- Avoid requiring external packages unless the user requested them.
- Make the task testable.
- Do not include markdown outside the JSON.
```

---

## 12. Hint Prompt

```text
You are a coding dojo coach.

The user is solving this problem:
{problem_without_solution_or_hidden_tests}

The user's current code:
{submission}

Hint level requested: {hint_level}

Rules:
- Do not reveal the full solution.
- Hint level 1: small conceptual nudge.
- Hint level 2: point toward the likely approach.
- Hint level 3: describe the algorithm, but do not write complete code.
- Keep the hint specific to the user's code.
```

---

## 13. Scoring Prompt

```text
You are a strict coding evaluator.

Grade the user's submission against the problem, rubric, expected concepts, canonical solution, and tests.

Problem:
{full_problem_json}

User submission:
{submission}

Return valid JSON only.

Schema:
{
  "score": number,
  "correctness": number,
  "edgeCases": number,
  "codeQuality": number,
  "complexity": number,
  "majorIssues": string[],
  "minorIssues": string[],
  "whatTheyDidWell": string[],
  "nextStepAdvice": string,
  "mistakeTags": string[],
  "shouldRevealSolution": false
}

Rules:
- Be strict but helpful.
- Do not reveal the full canonical solution.
- Focus on the user's submitted answer.
- Mention concrete missing cases.
- Prefer actionable feedback over generic encouragement.
```

---

## 14. JSON Repair Prompt

Local models will sometimes return malformed JSON. The app should automatically repair or retry.

```text
You returned invalid JSON.

Fix the response so it is valid JSON matching this schema:
{schema}

Invalid response:
{bad_response}

Return valid JSON only.
```

Recommended flow:

```text
1. Ask model for JSON.
2. Try to parse JSON.
3. Validate against schema.
4. If parse fails, run JSON repair prompt.
5. If validation fails, regenerate.
6. If still failing, show a clean app error.
```

## 15. Database Tables

Recommended SQLite tables:

```sql
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  language TEXT NOT NULL,
  topic TEXT NOT NULL,
  difficulty TEXT NOT NULL,
  mode TEXT NOT NULL,
  problem_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE submissions (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  code TEXT NOT NULL,
  score_report_json TEXT,
  created_at TEXT NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);

CREATE TABLE hints (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  hint_level INTEGER NOT NULL,
  hint_text TEXT NOT NULL,
  created_at TEXT NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);

CREATE TABLE model_settings (
  id TEXT PRIMARY KEY,
  model_path TEXT,
  runtime TEXT NOT NULL,
  context_size INTEGER,
  gpu_layers INTEGER,
  temperature REAL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

## 16. Code Execution Strategy

Do not include arbitrary code execution in the first version.

### Version 0.1

LLM-only generation, hinting, and scoring.

Benefits:

- Much faster to build.
- Avoids sandbox complexity.
- Validates the product loop.
- Still useful as a practice coach.

### Version 0.2

Add Python execution.

Rules:

- Run with timeout.
- Use a temporary directory.
- Do not run inside the main app process.
- Capture stdout/stderr.
- Limit file access where possible.
- Never allow network access if avoidable.
- Show public test results.
- Keep hidden tests internal.

### Version 0.3

Add JavaScript/TypeScript execution.

### Version 0.4

Add SQL practice using local SQLite.

### Version 0.5

Add Docker-based sandbox option for stronger isolation.

## 20. Product Design Principles

### 1. The app owns structure

The LLM should not control the entire experience. The app should own:

```text
Session state
Prompt templates
Schemas
Validation
History
Scoring categories
Hint levels
Model lifecycle
```

### 2. The model provides intelligence

The model should handle:

```text
Problem generation
Hint generation
Code critique
Concept explanation
Follow-up recommendations
```

### 3. Scoring should become hybrid

Initial version:

```text
LLM-only scoring
```

Better version:

```text
Automated tests + LLM critique
```

Best version:

```text
Automated tests + static checks + LLM critique + historical weakness tracking
```

### 4. Keep the UX focused

Do not overbuild before the loop is fun and useful.

The critical experience is:

```text
I can ask for exactly what I want to practice, get a useful rep, struggle, get a hint, submit, and learn what to do better.
```

## 24. Final Recommendation

Build the app in two layers:

```text
Layer 1: Product loop
Language → topic → difficulty → problem → hint → submission → score → next rep

Layer 2: Local runtime maturity
Ollama prototype → llama.cpp sidecar → GGUF model manager → optional sandboxed execution
```

Do not start with sandboxing, model packaging, or adaptive learning complexity.

Start by making one local practice session genuinely useful.

Once the loop feels good, harden the runtime and packaging.
